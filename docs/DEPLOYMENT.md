# CoursePilot — Deployment

CoursePilot runs free on two services:

- **Render** runs the app: one Docker container holding the API and the built web app.
- **Neon** runs the PostgreSQL database.

Every push to `main` that passes CI deploys itself.

## 1. Why this setup

| Choice | Reason |
|--------|--------|
| A hosting platform, not a server of my own | No machine to patch, no web server or HTTPS certificates to manage. Render builds the repository's `Dockerfile` and gives it a public HTTPS address. |
| One container for the pages and the API | The sign-in cookie is `SameSite=Strict`. On a single origin it is always a first-party cookie, with no cross-site setup and nothing for a browser's third-party cookie blocking to break. One service also means one deploy and one URL. |
| Neon for the database | Render's free database is deleted 30 days after it is created. Neon's free database has no time limit. |
| Ohio region on both | Render's `ohio` and Neon's AWS `us-east-2` are in the same place and close to Toronto, so every query is a short hop. |
| Deploy only after CI passes | `render.yaml` sets `autoDeployTrigger: checksPass`. A commit that fails tests, lint or the image check is never deployed. |

### What "free" costs

These limits were checked in November 2026; plans change, so confirm them on each provider's
pricing page.

- **The app sleeps.** Render stops a free service after 15 minutes with no visitors, and the next
  visit wakes it in about a minute. The page appears once the server is up. Say so wherever the
  link is shared, for example: *"Hosted on a free tier: the first visit can take up to a minute."*
- **Hours.** Render gives 750 free instance hours a month. A single service sleeping when idle
  stays well inside that.
- **Database.** Neon's free plan has 1 GB of storage and 100 compute hours a month per project.
  Neon also sleeps after 5 minutes idle and wakes in under a second.
- **One instance.** The sign-in rate limits are kept in memory, which is correct for a single
  instance (see `DEVELOPMENT_ROADMAP.md`).

## 2. One-time setup

You need a GitHub account with this repository pushed to it, and free Neon and Render accounts,
both of which can sign in with GitHub.

### Step 1: Create the database on Neon

1. Sign in at [neon.com](https://neon.com) and create a project. Name it `coursepilot`, choose
   PostgreSQL 17 and the region **AWS US East 2 (Ohio)**.
2. On the project dashboard, open **Connect**. Copy the connection string; it starts with
   `postgresql://`.
3. Keep it private. It contains the database password.

The app accepts the string exactly as Neon gives it and names the driver itself.

### Step 2: Create the service on Render

1. Push the latest `main` to GitHub.
2. Sign in at [render.com](https://render.com) and choose **New → Blueprint**.
3. Connect the `CoursePilot` repository. Render reads `render.yaml` and proposes one free web
   service named `coursepilot`.
4. When it asks for `DATABASE_URL`, paste the Neon connection string.
5. Leave the others alone:
   - `JWT_SECRET` and `CALENDAR_LINK_KEY` are generated by Render, separately, so they always differ.
   - `CLIENT_IP_HEADER` is set by the Blueprint.
6. Choose **Apply**.

The first build takes a few minutes. When the service shows **Live**, open its address, such as
`https://coursepilot.onrender.com`.

On every start, the container runs the database migrations before it starts serving. The
first start creates every table in the empty Neon database.

### Step 3: Check it

1. Open the address and register an account.
2. Add a course, a task and your study hours, then generate a schedule.
3. Reload the page. You should still be signed in.

## 3. Everyday use

- **Deploying:** push to `main`. GitHub Actions runs every check; when they all pass, Render
  builds and deploys that commit. Nothing else is needed.
- **A failed deploy:** the previous version keeps running. Read the build log in the Render
  dashboard; the cause is usually the same thing a local `docker build .` would show.
- **Logs:** Render dashboard → the service → **Logs**. Lines are JSON with a request ID. A visitor
  who reports an error can be matched to its log line by that ID.
- **Changing the database:** add an Alembic migration as usual. The next deploy applies it on
  start.

## 4. Settings in production

| Variable | Where it comes from | Purpose |
|----------|---------------------|---------|
| `ENVIRONMENT` | `Dockerfile` (`production`) | Turns on the production checks and HSTS |
| `STATIC_DIR` | `Dockerfile` | The built web app the API serves |
| `PORT` | Render | The port to listen on |
| `DATABASE_URL` | You, once, from Neon | The database |
| `JWT_SECRET` | Generated by Render | Signs sign-in tokens |
| `CALENDAR_LINK_KEY` | Generated by Render | Encrypts stored calendar links |
| `CLIENT_IP_HEADER` | `render.yaml` | Which header holds the visitor's address, for rate limits |

The app refuses to start in production if `JWT_SECRET` is a development value,
`CALENDAR_LINK_KEY` is missing or equal to `JWT_SECRET`, or cookies are not marked secure.

**Never rotate `CALENDAR_LINK_KEY`.** Stored calendar links are encrypted with it, so a new key
would make them unreadable. `JWT_SECRET` can be rotated; everyone stays signed in, because the
long-lived refresh tokens are kept in the database, not signed with it.

## 5. Checking the visitor-address header after the first deploy

Render sits behind Cloudflare, which is expected to set `True-Client-IP` to the visitor's real
address and overwrite any value the visitor sends. That is what keeps the sign-in limits honest.
It is not documented by Render, so check it once the app is live:

```bash
URL=https://coursepilot.onrender.com
for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w "%{http_code} " -X POST "$URL/api/v1/auth/login" \
    -H 'content-type: application/json' -H "True-Client-IP: 203.0.113.$i" \
    -d '{"email":"nobody@example.com","password":"not-the-password"}'
done; echo
```

- **Good:** `401 401 401 401 401 429`. The edge replaced the made-up addresses with the real one,
  so the sixth attempt is limited.
- **Bad:** six `401`s. The header can be forged. Remove `CLIENT_IP_HEADER` in the Render dashboard.
  The limits then count the proxy's address, which is stricter for everyone but cannot be dodged.

## 6. For the portfolio

A short way to describe the deployment:

> Deployed as a single Docker image on Render, with the FastAPI backend serving the built React
> app, so the pages and API share one origin. PostgreSQL is hosted on Neon. GitHub Actions runs
> the backend and frontend test suites and smoke-tests the production image, and Render deploys
> only commits whose checks pass. Database migrations run automatically on each release.
